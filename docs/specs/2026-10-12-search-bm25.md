# Spec: ranked BM25 lexical search—`okfctl search` orders its matches by relevance

Roadmap: `2026-10-12-agent-memory-ports`, Increment 2.
Branch: `feat/search-bm25`  Base: `next` @ 634eeb1

## Problem

Core `okfctl search` matches concept nodes by case-insensitive substring (PRD
§6.3) and prints them in **path order**. On a real corpus that order carries no
signal: `okfctl search signature` on the `nf525-lne` bundle returns 41 matches,
and the first five are `README.md` and four `infocert-referential/` nodes that
mention the word in passing—the three nodes *titled* "signatures" sit further
down purely because of where they live in the tree. An agent that reads the
top-N of a lexical search (the memory-ports use case) reads the wrong nodes.

The okfctl-search plugin has the same gap from the other side: its hybrid mode
(Increment 5) needs a lexical **ranking** to fuse with the semantic one, and
today there is none to call.

## Design

### Ranking is consumer-side; the spec floor is untouched

OKF v0.2 §1 lists "prescribing storage, serving, or query infrastructure" as a
non-goal, so how a consumer orders search hits is not spec-defined. This change
adds no `validate` rule and no lint rule, and reads only what the spec already
defines: `title` (§4.1—a consumer MAY derive it from the file name, which
`okfctl` already does), `tags` (§4.1, optional), `type` (§4.1, required, open
vocabulary—an unknown type is ranked like any other, never rejected), and the
Markdown body. Reserved files (`index.md`, `log.md`, §3.1) are never ranked,
exactly as they are never search results today.

### The match set does not change; BM25 orders it

A node is a result exactly when it was one before: the query is a
case-insensitive substring of a requested field. BM25 only **orders** that set.
This is what makes `--sort path` byte-identical to today's output and keeps
every existing caller's recall:

- **Default `--sort score`:** BM25F score descending, ties broken by path
  ascending (a total, deterministic order).
- A node that matches by substring but shares no stemmed content token with the
  query (`ci` inside `decision`, `pa` inside `paiement`) scores 0 and follows
  every scored hit, in path order. It is still a result—dropping it would change
  recall, which this increment does not do.
- **`--sort path`:** today's order, byte for byte. Any other `--sort` value is a
  usage error.
- **Text output is unchanged**—same line format, no score column. **`--json`
  gains `score`**; the existing fields (`path`, `title`, `type`,
  `neighborhood`, `matched_on`) are unchanged in name, type and order.
- `--neighbors`/`--depth` (graph mode) are untouched.

### BM25F

The score is BM25F over four fields, stdlib only, computed in memory from the
loaded bundle on each run (no index file):

```
tf~(t, d)  = Σ_f  w_f · tf_f(t, d) / (1 − B + B · len_f(d) / avglen_f)
score(q,d) = Σ_t∈q  IDF(t) · tf~ · (K1 + 1) / (K1 + tf~)
IDF(t)     = log(1 + (N − df(t) + 0.5) / (df(t) + 0.5))
```

- `K1 = 1.2`, `B = 0.75`—the literature defaults, as named constants
  (`lexical.K1`, `lexical.B`).
- `N` is the number of concept nodes; `df(t)` counts nodes containing the
  stemmed **token** `t` in any weighted field. DF is per token, never per raw
  substring: under substring containment `pa` is "in" every one of
  `plateforme-agree`'s 81 nodes (IDF 0.006); counted on tokens it is in 60
  (IDF 0.30), so a two-letter acronym keeps a real weight.
- The `+1` inside the log keeps IDF positive even for a term in every node.
- Field frequencies are summed before saturation (BM25F), so a term in the
  title and the body is not double-saturated.
- Every float sum runs in a fixed order (terms sorted, fields in a fixed order,
  nodes by path), so scores are bit-for-bit reproducible.
- `--field title|tag|type|body` keeps only that field's weight; the others drop
  to 0 and leave both the score and the DF.

### One analysis chain, shared

Query and node text go through the `--lexical-gate` chain: tokenize on
non-letter/digit runes, lowercase, drop the closed stopword set, apply the light
suffix stemmer. That chain moves verbatim from `internal/search/lexgate.go` to a
new stdlib-only package, `internal/lexical`, which core and the plugin both
import (core must not depend on the plugin). `lexgate.go` keeps its names as
thin forwarders, so `--lexical-gate` output and its tests are unchanged. A
stopword-only query (`the`) has no content term: nothing is ranked, every match
scores 0, and the order is path order.

### Field weights—justified on the real corpus

`DefaultWeights = {title: 3, tags: 2, type: 1.5, body: 1}`. The real corpus
(three bundles, 159 concept nodes, market-fr @ 78db06e) shows why the order is
title > tags > type > body:

| field | avg tokens/node (nf525-lne · plateforme-agree) | what it is |
|---|---|---|
| title | 7.5 · 6.6 | the author's one-line statement of what the node *is* |
| tags | 5.2 · 5.7 | deliberate cross-cutting labels (`nf525`, `security`, `chaining`) |
| type | 2.0 · 1.2 | a coarse class: 8 and 10 distinct values; `Certification Requirement` covers 44 of 71 nodes |
| body | 945 · 995 | mentions everything in passing |

Weights were compared on 17 realistic queries (`signature`, `archiving`, `jet`,
`hash`, `duplicate`, `e-reporting`, `grand totals`, `receipt`, `invoice`,
`closing period`, `audit trail`, `certificate`, `data security`, `payment`,
`vat`, `ci`, `pa`)—16 of them rank at least one node on each large bundle—by
counting how often the top hit (and the top 5) is a node whose title or tags
name a query term:

| weights (title/tags/type/body) | nf525-lne top-1 | nf525-lne top-5 | plateforme-agree top-1 | plateforme-agree top-5 |
|---|---|---|---|---|
| uniform 1/1/1/1 | 11/16 | 36/80 | 7/16 | 23/74 |
| **default 3/2/1.5/1** | **13/16** | **40/80** | **8/16** | **26/74** |
| type>tags 3/1.5/2/1 | 13/16 | 40/80 | 8/16 | 25/74 |
| heavy 5/3/2/1 | 14/16 | 46/80 | 8/16 | 28/74 |
| body-first 1/1/1/3 | 11/16 | 33/80 | 7/16 | 23/74 |

(`ifpos-interface-cases`, 7 nodes, is flat at 4/10 and 4/28 under every
weighting—too small to discriminate.) Weighting the title and tags lifts the
top hit from 11 to 13 of 16 over uniform. Going heavier (5/3/2/1) buys one more
top-1 on one bundle, but the metric rewards title weight by construction, so
"more is better" is not evidence; past 3× a single passing title word starts to
outweigh a node that discusses the term throughout its body. Promoting `type`
above `tags` never helps, which matches the table above: a type value is shared
by up to 62% of a bundle and so carries little IDF anyway. The defaults stay
moderate and are a named variable (`lexical.DefaultWeights`) so a later change
can re-tune them against this same table.

### Reusable API (for hybrid fusion)

`internal/lexical` (stdlib only):

```go
const K1, B
type Weights struct{ Title, Tags, Type, Body float64 }
var DefaultWeights Weights
type Document struct{ Path, Title string; Tags []string; Type, Body string }
type Scored struct{ Path string `json:"path"`; Score float64 `json:"score"` }
func NewIndex(docs []Document, w Weights) *Index
func (*Index) N() int; DF(term string) int
func (*Index) Scores(query string) map[string]float64 // positive scores only
func (*Index) Rank(query string) []Scored              // score desc, path asc
func Rank(docs []Document, query string, w Weights) []Scored
func IDF(n, df int) float64
func SortScored([]Scored)
func Tokenize, Analyze, Terms, Stem, IsStopword
```

`internal/okf`:

```go
func RankBM25(b *Bundle, query string, field SearchField) []lexical.Scored
func LexicalDocuments(b *Bundle) []lexical.Document // concept nodes, path order
func FieldWeights(field SearchField) lexical.Weights
func RankResults(rs []SearchResult)                 // score desc, path asc
// SearchResult gains Score float64 `json:"score"`
```

`RankBM25` is purely term-wise (every node with a positive score, no substring
set), which is the right input for a rank fusion. A caller with candidate
filters filters `LexicalDocuments` first and calls `lexical.Rank`.
`okf.Search` keeps returning path order (with `Score` filled in), so no
existing caller changes behavior.

## Acceptance criteria

1. **Positive control:** a node whose title names the term outranks a node that
   mentions it once in its body (`lexical`, `okf` and `cmd` tests).
2. **Positive control:** a two-letter acronym's DF is counted on tokens and its
   IDF is non-trivial (`ci` test; `pa` on the real corpus, IDF 0.30 against
   0.006 by substring).
3. **Negative control:** a stopword-only query ranks nothing; its output equals
   path order.
4. **Negative control:** `--sort path` output is byte-identical to `next` on the
   whole real-corpus capture (11 queries × 5 field modes × 3 bundles, plus
   `--neighbors`), and `--json --sort path` differs only by the added `score`.
5. The default-order output is a permutation of the `next` output for every
   capture (same match set).
6. `--lexical-gate` tests pass unchanged; `validate` and `lint --strict` on the
   real corpus are byte-identical before and after.
7. Top-5 for the pinned queries is recorded before/after in the PR.
